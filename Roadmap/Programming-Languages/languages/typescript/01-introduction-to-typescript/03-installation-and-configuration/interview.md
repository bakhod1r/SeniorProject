## Junior Interview Questions

### Q1: How do you install TypeScript in a project?

> Install it locally as a dev dependency:
> ```bash
> npm install --save-dev typescript
> ```
> This records the version in `package.json` and makes `tsc` available via `npx tsc` or npm scripts. It is a dev dependency because TypeScript is only needed at build time, not at runtime.

### Q2: What is the difference between a local and a global install?

> A **local** install (`npm install -D typescript`) puts TypeScript in the project's `node_modules` and pins its version in `package.json`. A **global** install (`npm install -g typescript`) makes `tsc` available system-wide but is shared across all projects, leading to version mismatches. Local installs are recommended for reproducibility.

### Q3: What does `npx tsc` do?

> `npx` runs the locally installed `tsc` binary from `node_modules/.bin` if present, otherwise downloads it temporarily. It is the standard way to invoke the project's pinned compiler without a global install.

### Q4: How do you generate a `tsconfig.json`?

> ```bash
> npx tsc --init
> ```
> This creates a documented `tsconfig.json` with sensible defaults (`strict: true`, `skipLibCheck: true`) and many commented-out options you can enable as needed.

### Q5: Why can't you run a `.ts` file directly with `node` (traditionally)?

> Node executes JavaScript, not TypeScript. You must compile `.ts` → `.js` first (`tsc`), then run the `.js`. Alternatively, tools like `tsx` or `ts-node` compile on the fly. (Recent Node versions can strip types directly, but that does not type-check.)

### Q6: What are `src/` and `dist/`?

> Conventions: `src/` holds your source `.ts` files; `dist/` holds the compiled `.js` output. You configure this with `"rootDir": "src"` and `"outDir": "dist"`. `dist/` should be gitignored because it is regenerated by the build.

### Q7: What does `tsc --noEmit` do?

> It type-checks the project and reports errors but writes no output files. It is the standard CI command to fail a build on type errors without producing artifacts.

## Middle Interview Questions

### Q8: How do you pin the TypeScript version, and why?

> Use an exact version (no caret):
> ```json
> { "devDependencies": { "typescript": "5.4.5" } }
> ```
> TypeScript does not follow strict semver — minor releases can add new type errors as the checker improves. Pinning prevents surprise build breakages and keeps every machine and CI on the identical compiler.

### Q9: When would you set `moduleResolution: "Bundler"` vs `"NodeNext"`?

> Use `Bundler` when a bundler (Vite, esbuild, webpack) compiles your TypeScript and resolves modules — pair it with `noEmit: true`. Use `NodeNext` when `tsc` itself emits JavaScript for Node, which requires `.js` extensions on relative imports and honors `package.json` `exports`/`type`.

### Q10: Describe a good `package.json` scripts setup for a TS project.

> ```json
> {
>   "scripts": {
>     "dev": "tsx watch src/index.ts",
>     "build": "tsc",
>     "typecheck": "tsc --noEmit",
>     "start": "node dist/index.js"
>   }
> }
> ```
> `dev` gives a fast loop via `tsx`, `typecheck` is the CI gate, `build` produces output, `start` runs it.

### Q11: What is the difference between `tsc`, `ts-node`, and `tsx`?

> `tsc` compiles `.ts` to `.js` files. `ts-node` runs `.ts` directly with optional type-checking (slower). `tsx` runs `.ts` directly using esbuild to strip types (very fast, no type-check). A common modern setup is `tsx` for dev plus `tsc --noEmit` for the type gate.

### Q12: How do you ensure your editor matches your build's TypeScript version?

> Commit `.vscode/settings.json` with:
> ```json
> { "typescript.tsdk": "node_modules/typescript/lib" }
> ```
> This makes VS Code's language service use the project's pinned TypeScript instead of its bundled copy, so editor diagnostics match `tsc`.

### Q13: What is `skipLibCheck` and what is the trade-off?

> `skipLibCheck: true` skips type-checking `.d.ts` files in `node_modules`, which is usually the largest chunk of compile work. The trade-off: it can hide genuine conflicts between declaration files from different packages. Most teams enable it for speed.

### Q14: Why is `isolatedModules` important in bundler-based setups?

> Single-file transpilers (esbuild, SWC, Babel) cannot see across files, so constructs like cross-file `const enum` or certain re-exports break. `isolatedModules: true` makes `tsc` flag any code a single-file transpiler cannot handle correctly, keeping the bundler's output sound.

### Q15: How do you add types for a JavaScript library that has none?

> Install the DefinitelyTyped package if it exists:
> ```bash
> npm install -D @types/lodash
> ```
> If none exists, write a local ambient declaration:
> ```typescript
> declare module "untyped-lib" { export function go(x: string): number; }
> ```

## Senior Interview Questions

### Q16: How do you guarantee reproducible builds across machines and CI?

> Four levers: (1) pin TypeScript and `@types/*` exactly; (2) commit `package-lock.json`; (3) run `npm ci` (not `npm install`) everywhere so installs come strictly from the lockfile; (4) add `overrides` to force a single TypeScript version in the tree. Together they make the same compiler with the same config run in every context.

### Q17: How do project references improve monorepo build performance?

> Each package sets `composite: true` and emits `.d.ts` plus a `.tsbuildinfo` cache. With `tsc -b`, the build topologically sorts the reference graph and rebuilds only stale packages and their dependents; downstream packages type-check against pre-computed `.d.ts` instead of re-parsing upstream source. No-change rebuilds finish in well under a second.

### Q18: What goes in a CI type-checking pipeline?

> ```yaml
> - run: npm ci
> - run: npm run typecheck   # tsc -b --noEmit
> - run: npm run build       # tsc -b
> ```
> Separate the type gate from the build artifact for clearer failures, and cache `**/*.tsbuildinfo` for fast PR feedback (with a clean rebuild for releases to avoid stale-cache bugs).

### Q19: How do you standardize TypeScript config across many repos?

> Publish a shared base config package (e.g., `@acme/tsconfig-base`) or adopt community bases (`@tsconfig/node20`, `@tsconfig/strictest`) and have every repo `extends` it. This gives one source of truth; repos override only `rootDir`/`outDir`/`include`. Governance can diff `tsc --showConfig` to detect drift.

### Q20: Describe a safe TypeScript upgrade process for a large codebase.

> Bump in a dedicated branch, run the full `tsc --noEmit`, capture the new-error delta, fix or document each one (never blanket-disable strict), and merge only on a green type gate. Pinning is what kept CI stable until this deliberate, reviewable upgrade.

### Q21: How do you incrementally add TypeScript to a large JavaScript project?

> Start with `allowJs: true`, `checkJs: false`, and a relaxed `strict`. Migrate file-by-file, optionally enabling `checkJs` for JSDoc-typed files. Tighten strict flags one at a time across separate PRs (`noImplicitAny`, then `strictNullChecks`, etc.) so each step is reviewable rather than a single giant breakage.

## Professional / Deep-Dive Questions

### Q22: What does `npm install typescript` physically create, and how is `tsc` wired?

> It extracts the package to `node_modules/typescript/` (the compiler is `lib/tsc.js`, plain JavaScript) and creates shim launchers in `node_modules/.bin/tsc` and `.../tsserver`. `npm run` and `npx` prepend `node_modules/.bin` to PATH, so they invoke the local compiler. There is no native binary — TypeScript runs on Node.

### Q23: How does an editor decide which TypeScript version to use?

> VS Code checks, in order: the `typescript.tsdk` setting → an explicitly selected workspace version → its own bundled TypeScript. The language service runs in a `tsserver` process that shares the type-checker core with `tsc`, so when versions match, editor diagnostics equal `tsc --noEmit`. Committing `typescript.tsdk` eliminates editor/CI mismatch.

### Q24: What is `tsserver` and how does it relate to `tsc`?

> `tsserver` is the long-running language service process the editor talks to over a JSON/stdio protocol. It maintains an in-memory `Program` and incrementally updates it on each keystroke, serving completions, hovers, diagnostics, and refactors from the same checker `tsc` uses. It is `tsc`'s interactive counterpart.

### Q25: How does `tsc` resolve `tsconfig.json` and merge `extends`?

> Bare `tsc` looks for `tsconfig.json` in the current directory and walks up parents. With `extends`, `compilerOptions` are shallow-merged (child wins per key), but `files`/`include`/`exclude` are **not** inherited. Relative paths resolve relative to the config that defines them. Verify the result with `tsc --showConfig`.

### Q26: How does incremental compilation work internally?

> With `incremental: true`, `tsc` writes a `.tsbuildinfo` containing file hashes, the dependency map, and a snapshot of `compilerOptions`. On the next run it re-hashes files and recompiles only those changed plus their type-dependents. Changing `compilerOptions` invalidates the snapshot and forces a full rebuild.

### Q27: Why might `npm ls typescript` show two versions, and why is that bad?

> A transitive dependency can declare its own `typescript`, producing a second copy in the tree. Two compilers can emit inconsistent `.d.ts` or make the editor and build disagree. Fix with `overrides: { "typescript": "5.4.5" }` to dedupe to one version.

## Scenario Questions

### S1: "My editor shows no errors but CI fails with type errors."

> The editor is likely using its bundled TypeScript, not the pinned project version. Set `typescript.tsdk` to `node_modules/typescript/lib` and select the workspace version. Also confirm `npm ls typescript` shows a single version.

### S2: "After switching to `module: NodeNext`, imports fail at runtime."

> Native ESM under `NodeNext` requires `.js` extensions on relative imports (even in `.ts` source) and `"type": "module"` in `package.json`. Add the extensions and the type field, then rebuild.

### S3: "Our monorepo's full type-check takes 90 seconds."

> Introduce project references: set `composite: true` per package, define `references`, and switch to `tsc -b`. Enable `skipLibCheck` and `incremental`, and cache `.tsbuildinfo` in CI. Profile remaining cost with `tsc --extendedDiagnostics` and `--generateTrace`.

### S4: "A junior committed the `dist/` folder and it keeps causing merge conflicts."

> Add `dist/` to `.gitignore`, remove it from tracking with `git rm -r --cached dist`, and ensure CI rebuilds it. Build output should never be versioned.

### S5: "We need to upgrade from TypeScript 5.3 to 5.5 but fear breakage."

> Do it in an isolated PR: bump the pinned version, run `tsc --noEmit`, capture the new-error delta, fix each error with documented reasoning, and merge only when the type gate is fully green. Never disable strict flags to force it through.

### S6: "Should we install TypeScript globally for our CI runners?"

> No. Install it locally and run via `npm ci` + npm scripts. A global install on the runner can drift from the project's pinned version and break reproducibility. The lockfile-driven local install is the single source of truth.

## Extended Q&A With Discussion

These questions go deeper, with the kind of back-and-forth a senior interviewer pushes for.

### Q28: Walk me through what happens, end to end, when a developer types `npx tsc` in a project.

> 1. `npx` checks `node_modules/.bin` for a `tsc` shim. In an installed project it is there.
> 2. The shim is a tiny Node launcher that `require`s `node_modules/typescript/lib/tsc.js`.
> 3. `tsc.js` looks for `tsconfig.json` in the current directory (walking up if absent).
> 4. It resolves `extends`, merges `compilerOptions`, and builds the file list from `include`/`exclude` plus imported files.
> 5. It constructs a `Program`, parses, binds, type-checks, and (unless `noEmit`) emits `.js`/`.d.ts`/`.map` into `outDir`.
> 6. Diagnostics are printed; a non-zero exit code signals errors.
>
> *Follow-up:* "What if there is no local install?" → npx checks its cache, then downloads the package temporarily — slower and not version-pinned, which is why a local install is preferred.

### Q29: A teammate says "let's just install TypeScript globally so we don't repeat it per project." How do you respond?

> Global installs cause version drift: project A may need 5.2, project B 5.5, and a single global `tsc` cannot satisfy both. Worse, CI and each developer's machine can have different globals, so builds are not reproducible. The cost of a local devDependency is trivial (it is cached by npm), and it pins the version in `package.json`. I would standardize on local installs plus `npx`/npm scripts and reserve global installs for throwaway experiments only.

### Q30: How do you decide between `tsc` emitting JS versus a bundler emitting it?

> If the target is Node and you want a simple, dependency-free build, let `tsc` emit with `module: NodeNext`. If the target is the browser, or you need bundling/tree-shaking/asset handling, use a bundler (Vite/esbuild/webpack) for emit and run `tsc --noEmit` purely as the type gate, with `isolatedModules: true` so single-file transpilation stays correct. The deciding factors are the runtime, the need for bundling, and build speed.

### Q31: Explain the role of `package-lock.json` in reproducible TypeScript builds.

> The lockfile records the exact resolved version and integrity hash of every dependency, including TypeScript and all `@types`. `npm ci` installs strictly from it, so every machine and CI runner gets byte-identical dependencies. Without committing the lockfile, two `npm install` runs days apart can resolve different versions, reintroducing the non-reproducibility that pinning was meant to prevent.

### Q32: What is the difference between `module` and `moduleResolution`, and why do both exist?

> `module` controls the **output** module format `tsc` emits (CommonJS `require` vs ESM `import`). `moduleResolution` controls how `tsc` **finds** modules referenced by imports during checking. They are separate because you can, for example, author ESM but resolve like a bundler. For Node you typically pair `NodeNext`/`NodeNext`; for bundlers, `ESNext`/`Bundler`.

### Q33: Your CI is slow because of TypeScript. What is your investigation order?

> First, `tsc --extendedDiagnostics` to see whether parse, bind, check, or emit dominates (usually check). Then enable `skipLibCheck` and `incremental`, and cache `.tsbuildinfo` in CI. If it is a monorepo, introduce project references and `tsc -b`. If a few files are pathological, `--generateTrace` + `analyze-trace` to find expensive generic instantiations. Each step is measured, not guessed.

### Q34: How would you add types incrementally to a 500-file JavaScript codebase?

> Enable `allowJs: true`, `checkJs: false`, and relaxed `strict`. Rename and migrate files to `.ts` one at a time, optionally enabling `checkJs` for JSDoc-annotated JS. Turn on strict sub-flags one per PR — `noImplicitAny` first, then `strictNullChecks`, etc. — so each change is reviewable and the type errors arrive in manageable batches rather than a single overwhelming wall.

### Q35: Why might `tsc --showConfig` be one of your most-used debugging commands?

> Because `extends`, path-rebasing, default inference (`moduleResolution` derived from `module`), and CLI overrides make the *effective* config non-obvious. `--showConfig` prints exactly what `tsc` will use after all merging, so I can confirm `outDir`, `strict`, `moduleResolution`, and the file globs are what I expect — catching config drift and `extends` surprises instantly.

## More Junior/Middle Depth Questions

### Q36: What is the purpose of `include`, `exclude`, and `files` in `tsconfig.json`?

> `files` is an explicit list (no globs). `include` is glob patterns of files to compile. `exclude` removes files from what `include` matched (and defaults to `node_modules`, `dist`, etc.). Important nuance: `exclude` does not stop a file from entering the program if another included file imports it — to truly keep a file out, nothing may import it.

### Q37: Why does `tsc --init` set `module: commonjs` and `target: es2016` by default, and should you keep them?

> Those conservative defaults maximize compatibility on any Node version out of the box. For modern projects you usually override them: `target: ES2022` for current Node, and `module: NodeNext` (with `"type": "module"`) for native ESM. The defaults are a safe floor, not a recommendation for new code.

### Q38: What does `esModuleInterop` do and why is it on by default in generated configs?

> It adds interop helpers so importing a CommonJS module with a default import (`import express from "express"`) works as developers expect, instead of requiring `import * as express`. It is on by default because the old behavior was a frequent footgun. It implies `allowSyntheticDefaultImports`.

### Q39: How do you run a TypeScript file as a quick script without setting up a build?

> Use `tsx`: `npx tsx script.ts`. It transpiles with esbuild and runs immediately, reading your `tsconfig.json` for `target`/`paths`. For one-offs you can also use recent Node's `--experimental-strip-types`. Neither type-checks, so keep `tsc --noEmit` for correctness.

### Q40: What is `resolveJsonModule` and when do you need it?

> It lets you `import data from "./data.json"` with the JSON typed structurally. Without it, importing JSON is an error. Enable it when your code imports JSON files directly (config, fixtures), and pair it with a bundler/`module` setting that supports JSON imports at runtime.

## System-Design-Flavored Questions

### SD1: Design the TypeScript setup for a company with 40 repos and 60 engineers.

> - **One source of truth:** publish `@acme/tsconfig-base` (extending `@tsconfig/strictest`); every repo `extends` it and overrides only `rootDir`/`outDir`.
> - **Pinning:** TypeScript and `@types/*` exact-pinned; `.npmrc` with `save-exact=true`; `overrides` dedupe to one TS version per repo.
> - **Toolchain:** `.nvmrc` + `engines` + Corepack so Node/npm match everywhere.
> - **CI:** reusable workflow running `npm ci` → `tsc -b --noEmit` → `tsc -b`, caching `.tsbuildinfo` and `~/.npm`.
> - **Editor:** committed `.vscode/settings.json` pinning the workspace TS version.
> - **Governance:** a scheduled "upgrade TypeScript" PR per minor release, gated by a green type-check; an ESLint rule banning `as any` and bare `@ts-ignore`.

### SD2: How do you keep editor diagnostics and CI in lockstep across the whole org?

> The editor must run the same compiler as CI. Enforce `typescript.tsdk: node_modules/typescript/lib` in a committed workspace setting, pin TS exactly, and dedupe with `overrides`. Then `tsserver` (editor) and `tsc` (CI) are the same code on the same config — divergence becomes impossible by construction.

### SD3: A new hire's builds differ from everyone else's. Diagnose.

> Check, in order: (1) `node -v` / `npm -v` against `engines`/`.nvmrc`; (2) did they run `npm ci` or `npm install`?; (3) `npm ls typescript` for a stray second copy; (4) `npx tsc --version` vs the pinned one; (5) `npx tsc --showConfig` to confirm the effective config matches. One of these almost always explains the drift.

## Conceptual Comparison Questions

### C1: `tsc --noEmit` vs `tsc` vs `tsc -b` — when is each correct?

> - `tsc --noEmit`: the **type gate**. Checks types, writes nothing. Use in CI and pre-commit hooks.
> - `tsc`: a **single-project build**. Checks and emits per one `tsconfig.json`. Use for simple apps/libraries.
> - `tsc -b`: **build mode** for project references. Reads `references`, builds in dependency order, incremental via `.tsbuildinfo`. Use in monorepos.

### C2: Local install vs `npx` (no install) vs global — trade-offs table.

| Approach | Reproducible | Speed | Use for |
|----------|--------------|-------|---------|
| Local devDependency | Yes (pinned) | Fast after install | Every real project |
| `npx` without install | No (may fetch latest) | Slow first run | Throwaway commands |
| Global | No (shared across repos) | Fast | Quick experiments only |

### C3: `tsx` vs `ts-node` vs `tsc && node` for running TypeScript.

> - `tsx`: esbuild-based, strips types, **very fast, no type-check**. Best dev/test loop.
> - `ts-node`: can type-check while running (slower) or `--transpile-only`. Older, heavier.
> - `tsc && node`: explicit two-step, **production standard**, full type-check, real artifact in `dist/`.

### C4: `module: NodeNext` vs `Bundler` vs `CommonJS`.

> - `NodeNext`: native Node ESM, honors `package.json` `exports`/`type`, requires `.js` import extensions.
> - `Bundler`: a bundler resolves and emits; extensions optional; pair with `noEmit: true`.
> - `CommonJS`: classic `require` output for legacy or simple Node setups.

## "Explain to a Junior" Questions

Senior candidates are often asked to teach a concept simply.

### E1: Explain to a junior why we don't commit the `dist/` folder.

> "`dist/` is generated by the compiler from your `src/` files — like a baked cake from a recipe. We commit the recipe (`src/`), not the cake. Committing `dist/` causes merge conflicts, bloats the repo, and can go stale. CI bakes a fresh copy on every deploy, so the cake is always made from the latest recipe."

### E2: Explain to a junior why the editor sometimes disagrees with the build.

> "VS Code ships its own copy of TypeScript, which may be a different version than the one our project pins. The build uses the project's version. If they differ, the editor and build can disagree. We fix it by telling VS Code to 'Use Workspace Version' — then the editor checks your code with the exact same compiler the build uses."

### E3: Explain to a junior why we pin the TypeScript version exactly.

> "TypeScript gets stricter over time — a newer version can flag mistakes the old one missed. That is good, but we don't want it to happen by surprise in the middle of a sprint when someone reinstalls. So we lock the version. When we want the new checks, we upgrade on purpose, in its own pull request, and fix whatever it finds."

## Behavioral / Experience Questions

### B1: Tell me about a time a TypeScript upgrade broke your build. What did you do?

> Strong answers describe: isolating the bump in a dedicated branch, running `tsc --noEmit` to capture the full error delta, triaging errors into "real bugs the new checker caught" vs "stricter-but-equivalent" cases, fixing or narrowing each rather than disabling strict flags, and merging only on a green type gate. The lesson articulated: pinning is what kept everyone else unblocked until the upgrade was ready.

### B2: How did you standardize TypeScript across teams that disagreed on config?

> Look for: establishing a shared base config as the non-negotiable floor (strict, module resolution), while allowing teams to override leaf options (`outDir`, `paths`). Buy-in came from removing pain — fewer "works on my machine" issues — not from mandate. Governance via a `tsc --showConfig` drift check kept it honest.

### B3: Describe a build-performance problem you solved.

> Good structure: measured first (`--extendedDiagnostics` showed check time dominating), applied targeted fixes (`skipLibCheck`, project references, cached `.tsbuildinfo`), re-measured, and reported concrete before/after numbers. The point being assessed is measurement discipline, not the specific flags.

## Tricky "Gotcha" Questions

### G1: Will `tsc src/index.ts` use your `tsconfig.json`?

> No. Passing an explicit input file makes `tsc` ignore `tsconfig.json` entirely and fall back to compiler defaults — no `outDir`, `strict` off. Use bare `tsc` or `tsc -p tsconfig.json`.

### G2: Does a `paths` alias work when you run the emitted JS with Node?

> No, by itself. `paths` only affects `tsc`'s type resolution; it is not rewritten in the emitted JavaScript. Node will fail to resolve `@/...` at runtime unless you add a runtime resolver, use Node subpath `imports`, or rewrite paths during build.

### G3: If `strict: true` is set, can `noImplicitAny` still be off?

> Yes — an explicit `"noImplicitAny": false` after `strict: true` overrides just that flag. The config looks strict but has a hole. Audit for individual strict-flag overrides.

### G4: Is `npx tsc` guaranteed to use your project's version?

> Only if a local install exists. `npx` prefers `node_modules/.bin`, but with no local install it may download and run the latest from the registry. Always install TypeScript locally so `npx tsc` is deterministic.

## One-Line Command Reference for Interviews

Memorize these — interviewers expect instant recall.

```bash
npm install -D typescript        # local pinned install
npx tsc --init                   # generate tsconfig.json
npx tsc                          # compile
npx tsc --noEmit                 # type-check only (CI gate)
npx tsc --watch                  # rebuild on save
npx tsc -b                       # build project references
npx tsc -b --clean               # delete reference outputs
npx tsc --showConfig             # print resolved config
npx tsc --listFiles              # files in the program
npx tsc --traceResolution        # debug module resolution
npx tsc --extendedDiagnostics    # per-phase timing
npm ci                           # reproducible install (CI)
npm ls typescript                # detect duplicate compilers
node -p "require.resolve('typescript')"  # where TS resolves
```

## Final Tips

- Always justify a config choice with the **runtime** it targets.
- Prefer **local + pinned** over global in every answer.
- Separate **type-check (gate)** from **build (artifact)** in CI discussions.
- For monorepos, reach for **project references** and `tsc -b`.
- When stuck, say **"I'd run `tsc --showConfig` / `--extendedDiagnostics` to see the real state"** — it signals a diagnostic mindset.
