# go generate — Middle

## 1. What `go generate` actually does

`go generate` walks the requested packages, parses each `.go` file, and for every line that **starts** with `//go:generate ` it executes the rest of the line as a shell-less command (`exec.Command`). It does not run the Go compiler, it does not affect imports, it does not write anything itself — everything that ends up in your repo is produced by the tool you invoked.

Key consequence: `go build` and `go test` **do not** run `go generate`. Generated files exist on disk only because somebody ran the command. CI must guard that they are up to date.

---

## 2. How directives are discovered

- Files matched by the build constraints of your *current* environment are scanned.
- Files filtered out by build tags or `_GOOS`/`_GOARCH` suffixes are skipped — so a `//go:generate` in `linux_only.go` doesn't run on macOS unless you set `GOOS=linux`.
- Test files (`_test.go`) are scanned too.

If a directive isn't firing, the first thing to check is whether the file is included by the current build.

---

## 3. Environment variables Go injects

Inside the generator, Go sets a handful of variables you can rely on:

| Variable | Value |
|----------|-------|
| `$GOARCH` | Target architecture (`amd64`, `arm64`, ...) |
| `$GOOS` | Target operating system |
| `$GOFILE` | Base name of the source file containing the directive |
| `$GOLINE` | Line number of the directive in `$GOFILE` |
| `$GOPACKAGE` | Package name of `$GOFILE` |
| `$GOROOT` | Go installation path |
| `$DOLLAR` | A literal `$` (workaround because `$` is special) |
| `$PATH` | Inherited from your shell |

```go
//go:generate echo file=$GOFILE pkg=$GOPACKAGE line=$GOLINE
```

Generators like `stringer` use `$GOFILE`/`$GOPACKAGE` internally; you rarely set these by hand.

---

## 4. Conventional output naming

Most generators write to a predictable filename so reruns overwrite cleanly:

| Generator | Input | Output |
|-----------|-------|--------|
| `stringer -type=Color` | `color.go` | `color_string.go` |
| `mockgen -destination=mocks/foo.go` | interface in `foo.go` | `mocks/foo.go` |
| `protoc-gen-go` | `foo.proto` | `foo.pb.go` |

Generated files are usually marked with a header like `// Code generated by ... DO NOT EDIT.`, which `go vet`, code review tooling, and some linters honor.

## 5. Pinning the generator version

Three patterns, in order of preference:

```go
// 1. Inline pin (Go 1.16+) — best for reproducibility, no go.mod pollution
//go:generate go run golang.org/x/tools/cmd/stringer@v0.24.0 -type=State
```

```go
// 2. tools.go file (pre Go 1.24) — version comes from go.mod
//go:build tools
package tools
import _ "golang.org/x/tools/cmd/stringer"
```

```go
// 3. go.mod tool directive (Go 1.24+) — first-class tool dependency
tool golang.org/x/tools/cmd/stringer
```

Never use `@latest` in a committed directive. It is non-reproducible and silently changes output across machines and across time.

---

## 6. Restricting which directives run

`go generate` accepts `-run` to filter directives by a regex matched against the **command line** of each directive:

```bash
go generate -run="stringer" ./...   # only run stringer directives
go generate -run="protoc"   ./...
```

This is useful when one of your generators is slow (e.g., protoc) and you only changed an enum. The matching is **substring** by default unless you anchor the regex.

There is also a `//go:generate:` form for *conditional skipping* — most teams skip this and use `-run` instead.

---

## 7. Working directory and paths

Each generator runs with **CWD set to the directory of the file** containing the directive. So:

```go
//go:generate protoc -I=. --go_out=. foo.proto
```

is correct: `foo.proto` is relative to the source directory, not your shell's `pwd`. This is why you almost never need `cd` inside a generator command.

---

## 8. Combining generation with regular code

A practical pattern: one directive per type, placed right above the type so reviewers see it together.

```go
//go:generate go run golang.org/x/tools/cmd/stringer@v0.24.0 -type=Status
type Status int

const (
    Pending Status = iota
    Active
    Closed
)
```

Anti-pattern: a single file full of `go:generate` directives unrelated to the surrounding code. It hides which generator owns which output and confuses cross-references.

---

## 9. CI: verify generated code is current

The standard CI check:

```bash
go generate ./...
git diff --exit-code        # fails if anything changed
```

If a developer forgot to re-run after changing a `.proto` or an enum, CI rejects the PR. This is how teams keep generated files reliably in sync with their sources.

---

## 10. Trade-offs summary

| Concern | Generated code | Hand-written |
|---------|----------------|--------------|
| Maintenance | Re-run on change | Edit by hand |
| Review noise | Large diffs in `_gen.go` files | Smaller, focused diffs |
| Onboarding | Need to learn each generator | Just read code |
| Correctness on schema change | Automatic | Easy to forget |
| Build speed | Pay once; cached | None |

Lean on generation when the input drives the code (enums, schemas, IDLs). Skip it when there is no source of truth besides the code itself.

---

## 11. Summary

`go generate` runs the commands inside `//go:generate` comments — it is not a compiler step and is not invoked by `go build`. Use `go run tool@version` to pin generators inline, name outputs with conventional `_gen.go`/`_string.go` suffixes, restrict invocations with `-run`, and let CI enforce that generated files are up to date.
